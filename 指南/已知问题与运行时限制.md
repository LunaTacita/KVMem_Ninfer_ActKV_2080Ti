# 指南 · 已知问题与运行时限制

> 本页记录**运行期的已知限制、影响与规避方式**，供使用者与接收方 agent 排障时查阅。
> `README.md` 面向“能做什么、怎么用”；本页面向“哪些路径有边界、边界在哪、怎么绕开”。
> 所有条目均来自本项目的构建机实测（RTX 2080 Ti 11GB / sm_75 / 驱动 566.36 / CUDA 12.6），换硬件/驱动/模型后请重新确认。

---

## 1. 投机解码（MTP）——可选实验功能，默认关闭

**默认状态：关闭。** 启动脚本里 `$SPEC = ""` 且 `$DRAFT_TOKENS = ""`（两者必须同时留空；只给 `--spec mtp` 而不给 `--draft-tokens` 时引擎会报 `--draft-tokens require --spec` 并打印帮助退出）。

### 现象

- **单轮**、短上下文请求：开启后通常正常，且 decode 速度明显提升（draft=2 时接受率约 91%；构建机短上下文实测约 80 tok/s，同配置默认关闭 MTP 时约 51–52 tok/s）。
- **长多轮对话**（每轮等模型回复结束再发下一轮，触发 turn closure / KV restore）：
  在部分组合下可能触发 `cudaErrorMisalignedAddress` 并使进程退出（按 §12 的机制打印 `ninfer-serve: FATAL: …` 后以退出码 1 退出）；出现时机不固定，与请求时序、窗口与硬件组合相关。
- 使用默认（非投机）路径时，同一多轮场景表现稳定。

### 影响

- 多轮 Agent / 长对话场景请使用**默认路径**（本包已默认关闭 MTP，日常使用不受影响）。
- 需要速度时可尝试单轮短任务临时开启；进入多轮对话前请切回默认。

### 如何开启（实验）

编辑 `Start\启动_KVMem_Ninfer_ActKV_2080Ti.ps1`：

```powershell
$SPEC         = "mtp"
$DRAFT_TOKENS = "2"     # 实测 draft=2 优于 draft=4
```

> 开启即表示你接受该实验性功能的风险；生产/对外服务保持默认关闭。

### 技术边界说明

- 本项目对该可选路径做了**长期专项验证与数轮迭代测试**，覆盖 CUDA Graph、执行表映射、restore/publish、workspace 复用、profile 切换、数据搬运完整性、16 字节对齐、输出长度、工具调用格式等多个维度。
- 该现象与 **sm_75 + 本移植栈（small-T / int8 KV）+ 多轮 restore** 这一特定组合相关；上游预编译支持面（sm_80/86/89/120a）未覆盖该硬件组合，因此上游版本未包含针对该路径的适配。
- 结论：该功能被标记为**实验性（experimental）**、默认关闭；**常规（非投机）路径经过完整验收，可放心用于生产**。本项目会在上游相关更新出现时重新评估该实验功能的可用性。

## 2. n-gram 草稿——可选路径，默认关闭

- n-gram 草稿是引擎提供的**可选投机路径**（KVMem 模式下支持宽度 1..63，并发 >1 时会自动收窄），本包**默认关闭**（`--ngram-draft-tokens 0`），不作为生产推荐。
- 引擎对 **n-gram 表格式**有要求（仅 IQ4_NL / BF16 行格式）；外挂表时摘要与格式必须一致。不同模型制品是否自带 n-gram 表，请以 `模型包\MODELS.md` 为准。
- 本包未对 n-gram 路径做系统性收益验证（默认（非投机）路径已覆盖常规场景）。如需实验，建议从小宽度开始，并用真实多轮对话自行验证输出质量与长时间稳定性。

---

## 3. `active_kv_ssd` 判据在极端测试配置下的非确定性

只在**极端低内存测试配置**（可见集 384 / 强制 spill）下出现波动，**生产配置未复现**，因此：
- 不纳入本包验证范围（KVMem 专项回归按 14 项计，其中不含该探针）；
- 使用生产配方时不受影响。

---

## 4. 1M 全量 prefill 未纳入实测范围

已验证：**1M 起服成功**、`/v1/load` 报 `max_context 1048576`、287,269 token prefill 实测通过、105K 长上下文在 90% 深度处召回命中。
**未纳入本包实测范围**：一次请求读入 1M Token 的长文档（单请求预计数十分钟以上）。需要此类负载时请评估时延或自行分段。

---

## 5. `--lm-head-q6` / `--embedding-q6` 不可用

引擎要求 `text/output_head` / `text/token_embedding` 以 row-split Q8_G32 存储。本项目实测使用的 Bonsai 模型为三元量化格式，不满足该要求 ⇒ 这两个省显存选项在该制品上不可用。这是**模型制品的格式约束**，不是引擎缺陷；其他格式的模型可按同样要求自行测试。

---

## 6. 模型放在机械盘时加载很慢

新进程冷缓存加载可能只有 8~135 MB/s，日志看起来像停在加载阶段。复制到 NVMe 后起服约 5.5 s。建议模型与缓存目录都放 NVMe。

---

## 7. 判据脚本需要 PowerShell 7

`sm75_eval\run_*.ps1` 使用 PS7 语义；PS 5.1 的 `Invoke-RestMethod` 在这类 chat 负载上有已知转换问题。
**启动脚本本身** PS 5.1 / PS 7 都可以。

---

## 8. `--device-profile` 与容量分配

`--device-profile` 是**算子路由配置**（为每个算子选择在当前硬件档位下使用的 kernel 调度），**不是内存 / 池 / 模型层的自动分配开关**。上游自带内置档表 `src\runtime\engine\device_profiles.json`，其中**没有 2080 Ti（sm_75）内置档**；`auto` / `calibrate` 会在运行期测量并校准，结果缓存到 `%LOCALAPPDATA%\ninfer\device-profiles.json`。

本包**生产固定 `--device-profile off`**（启动脚本默认），原因：
- 本移植栈的 sm_75 路由已在**编译期**完成适配（架构白名单 +75、`NINFER_SM75` 等），不需要运行期校准；
- 运行期自动校准会按测量结果改变路由选择，可能偏离本包验证过的路径，带来正确性与长时间稳定性风险；
- 实测 `auto` 在本栈上也没有速度收益（off 51.1 vs auto 47–50 tok/s）；
- 如需实验校准，请自行验证正确性与长时间稳定性，不要手动改缓存文件当做调优。

**容量分配的实际口径**（与 `--device-profile` 无关）：
- 主机 KV 预算默认 `--kvmem-host-mib auto` = 物理内存 − 1 GiB，自动计算；
- 设备可见窗口由 `--kvmem-budget`（B）与 `--kvmem-gen-reserve`（R）决定，**不会自动选择**；
- 设备窗口装不下时，引擎**不崩溃**，直接报出「需要多少字节、权重加载后可用多少、本配置最大可启动窗口约多少 token / 每 lane」，并给出建议的 `--kvmem-budget` 值及更省显存的 KV 格式选项；按提示调整即可。

## 9. 环境前提：关闭 RTSS 等 OSD 注入类软件

**RTSS（RivaTuner Statistics Server）及同类 GPU OSD 覆盖层注入工具**可能影响**长时间运行的稳定性**（尤其长上下文 / 多轮判据）——问题出在**游戏内覆盖层的注入 / Hook**。
**跑长上下文 / 多轮判据前请关闭 RTSS 及其后台服务与注入模块。**
这是工程环境建议，不做代码兼容。

---

## 10. 快速自检顺序

遇到“起不来 / 答不对 / 很慢”，按此顺序排查：

1. `verify-engine.ps1` 是否 `ENGINE-PACK-OK`（包完整性、DLL 齐全）；
2. 路径是否**全 ASCII**；模型 sha256 是否与 `模型包\MODELS.md` 一致；
3. `/v1/models` 是否 200；真实 chat 请求 `content` 是否非空（`finish_reason` 是否 `length`）；
4. 是否误开了 MTP / n-gram（本页 §1、§2）；
5. 是否模型在机械盘（§6）；
6. 是否 UI 注入软件在跑（§9）；
7. 服务进程是否退出、日志是否有 `ninfer-serve: FATAL:`（见 §12）；WebUI 是否触发等待超时（见 §13）。

---

## 11. 长时间或多客户端连续使用后的输出多样性

- **现象**：在发送过**长上下文请求**（例如带完整对话历史与工具定义的 Agent 客户端，prompt 达数十K Token）之后，同一服务上新的简短对话可能出现**输出比平时更简短、更模板化**。构建机实测：WebUI 同一问题「你是谁？」，长上下文请求前回答约 240 token（分点详细版），之后降至约 70–120 token（简短、模板化版本）。**重启服务后恢复。**
- **影响**：不影响正确性、工具调用与功能可用性，但会影响回答风格与丰富度。
- **规避**：需要最佳输出多样性时，在长时间或多客户端连续使用后**重启服务**。
- **状态**：具体机制尚未定位；常规单客户端短会话场景一般不受影响。

## 12. 长上下文任务中的偶发 GPU 错误与退出行为

- **现象（偶发）**：在 200K+ Token 的长上下文任务中——即完成一次长 prefill 与长 decode 之后，新对话仍需要按长上下文重新 prefill 的场景、约 70K–80K Token 处——少数情况下会触发 `cudaErrorIllegalAddress`（日志中可见 `last host op: layer/prefill/gdn`）。触发与请求时序、窗口组合相关，**不稳定复现**：同一配置多次运行可能不出现。
- **退出行为**：遇到不可恢复的 CUDA / 内部错误时，进程打印 `ninfer-serve: FATAL: <详情>` 与重启提示后，以**退出码 1** 退出，不自动重启（是否重启由使用者决定）。
- **影响**：受影响的请求中断，需要重启服务后重试；已完成的其他请求结果不受影响。
- **规避 / 建议**：长任务分段处理；或把 `--max-context` 降到 262144（模型原生上下文，仍覆盖 200K 级任务）以降低换页压力；重启服务后重试。若希望协助定位，请保留 `logs\` 下对应日志（含 FATAL 行与末段日志）。

## 13. 内置 WebUI 的等待上限（默认 1 小时）

- WebUI 一次对话的等待上限由服务端 `--webui-request-timeout-ms` 控制（**默认 `3600000` = 1 小时**；`0` = 不设前端超时），服务端通过 `/props` 的 `webui.request_timeout_ms` 下发，WebUI 启动时读取并应用。
- 长 prompt 的 KVMem prefill 可能持续 15–30 分钟，默认 1 小时用于避免浏览器侧误报"服务器超时"。
- 调整方式：改启动脚本里的 `$WEBUI_REQUEST_TIMEOUT_MS` 后重启服务；`0` 表示只受浏览器 / 网络限制。

---

## 14. 极端长上下文（200K Token 级）下部分客户端的输出表现（现象记录）

- **现象**：在接近或超过 200K Token 的极端长上下文任务中，通过**内置 WebUI** 或 **Agent 类客户端**（带大量工具定义、长系统提示、多轮历史）使用时，可能观察到输出质量下降、内容重复、上一轮上下文接不上、工具调用不生效等表现；同一提示改用**直接调用 `/v1/chat/completions`（单轮、不带工具）**时，输出通常更稳定。
- **状态**：该现象**原因未完全定位**，本版作为已知限制记录，未做修复。
- **说明**：极端长上下文下的理解质量同样受模型能力与量化档位限制（本包实测制品为 27B 三元量化），部分表现可能源于模型侧而非框架侧。
- **时延参考**：极端长上下文任务的单次 prefill 可能需要 15–30 分钟（等待上限说明见 §13）。

## 15. KVMem 专项回归与测试范围

- 引擎当前注册 ctest **314 项**，绝大多数是上游引擎的单元测试；本包的**交付回归范围**是 `tests/experimental` 下的 **KVMem 专项 14 项**（15 个探针中排除 `active_kv_ssd`，见 §3）。
- 本交付二进制的专项结果：**14 项中 13 通过**。未通过的 `memory_ngram` 为偶发（同一命令手动复跑 2/2 通过），且生产默认关闭该路径（`--ngram-draft-tokens 0`），不影响生产默认配置。
- 全量 ctest（258 项）曾 100% 通过，覆盖上游引擎单元测试。
